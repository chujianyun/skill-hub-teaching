## 1. 使用的系统与方式

仓库采用最简化的环境变量驱动配置，没有引入任何配置框架（如 `@nestjs/config`、`dotenv-flow` 等），仅依赖 Node.js 原生 `process.env` 与 `dotenv`。
- 后端 NestJS 应用：在 `apps/server/src/main.ts` 顶部通过 `import 'dotenv/config'` 加载 `.env`，所有运行时参数直接从 `process.env` 读取。
- 前端 Vite 应用：在 `apps/web/vite.config.ts` 中直接读取 `process.env.WEB_PORT`、`process.env.API_TARGET`。
- 容器编排：通过根目录 `docker-compose.yml` 以 `environment:` 字段注入数据库连接串、端口、上传目录等。
- 示例模板：根级 `.env.example` 与 `apps/server/.env.example` 提供开发环境键名参考。

## 2. 关键文件

- `apps/server/src/main.ts` — 入口，加载 dotenv 并启动 Nest 应用，监听 `process.env.PORT`。
- `apps/server/.env.example` — 后端环境变量模板，定义 `DATABASE_URL`、`PORT`、`SESSION_COOKIE_SECURE`、`PRIVATE_UPLOAD_DIR`。
- `apps/web/vite.config.ts` — 前端构建/开发服务器配置，使用 `WEB_PORT`、`API_TARGET`。
- `docker-compose.yml` — 编排 PostgreSQL、server、web 三服务，集中声明运行期环境变量与卷挂载。
- `deploy/server.Dockerfile` / `deploy/web.Dockerfile` — 容器镜像构建时不嵌入配置，依赖运行期环境变量。
- `apps/server/src/app.setup.ts` — 应用初始化（全局前缀、cookie-parser、ValidationPipe、shutdown hooks），不含业务配置。
- `apps/server/prisma/schema.prisma` — 数据模型，连接字符串由外部 `DATABASE_URL` 注入（Prisma 约定）。
- `scripts/dev.mjs` / `scripts/setup.mjs` / `scripts/dev-db.mjs` — 开发脚本，复用根 `.env.example` 中的 `DB_PORT`、`HTTP_PORT` 等键。

## 3. 架构与约定

- **单一来源**：所有可配置项均以 `process.env.XXX` 形式暴露，无配置文件解析层、无默认值合并策略、无类型安全的 config service。缺少键或值为空即按 Node.js 默认行为处理（`undefined` 或空字符串）。
- **分层职责**：
  - `docker-compose.yml` 负责生产/集成环境的运行时配置（PostgreSQL 凭据、`DATABASE_URL`、`PORT=3000`、`PRIVATE_UPLOAD_DIR=/app/private-uploads`、`SESSION_COOKIE_SECURE=false`）。
  - `apps/server/.env.example` 与根 `.env.example` 负责本地开发键名约定（`DATABASE_URL`、`PORT`、`SESSION_COOKIE_SECURE`、`PRIVATE_UPLOAD_DIR`、`DB_PORT`、`HTTP_PORT`、`WEB_PORT`、`API_TARGET`）。
  - `vite.config.ts` 将 `WEB_PORT`、`API_TARGET` 用于本地开发代理到后端。
- **共享常量**：Nest 应用的 API 前缀来自 `@skill-hub/shared` 包的 `API_PREFIX`（见 `app.setup.ts`），属于编译期常量而非运行时配置。
- **测试隔离**：e2e 测试通过 `apps/server/test/setup-env.ts` 等独立脚本设置自身的环境，注释明确“main.ts 与 e2e 测试共用，保证测试打到的应用与线上配置一致”，避免污染主进程 env。

## 4. 约定与约束

- **环境变量命名**：全部使用大写下划线风格（`DATABASE_URL`、`SESSION_COOKIE_SECURE`、`PRIVATE_UPLOAD_DIR`、`WEB_PORT`、`API_TARGET`、`DB_PORT`、`HTTP_PORT`），未见小写或 camelCase 的自定义配置键。
- **必需 vs 可选**：代码中对部分变量提供了回退值——`process.env.PORT ?? 3001`（`main.ts`）、`Number(process.env.WEB_PORT ?? 5175)`（`vite.config.ts`）、`process.env.API_TARGET ?? 'http://localhost:3001'`；但 `DATABASE_URL` 在 Prisma 侧未提供默认值，缺失时会报错，因此对生产/容器部署是必需的。
- **安全边界**：`.env` 文件本身未被纳入版本控制（`.gitignore` 生效），仅 `.env.example` 提交作为键名契约；Docker Compose 中的数据库密码以明文写入 compose 文件，适用于演示场景。
- **Cookie 安全开关**：`SESSION_COOKIE_SECURE` 在开发模板中设为 `false`，在 docker-compose 中也显式传入 `false`，表明该标志位由上层配置决定，后端不硬编码。
- **上传目录**：`PRIVATE_UPLOAD_DIR` 在 Compose 中映射为 `/app/private-uploads` 卷，确保容器重启后 Skill 包持久化；本地开发则需自行创建对应路径。
- **无 feature flags / 多环境切换**：仓库没有 staging/prod 等多套配置文件，也没有条件分支根据环境变量切换行为（除 cookie secure 外），环境差异完全通过外部注入实现。
- **Prisma 连接**：遵循 Prisma 官方约定，通过 `DATABASE_URL` 环境变量注入连接串，schema 中不内嵌凭据。

总体而言，这是一个极简的“环境变量即配置”方案：没有配置 schema 校验、没有默认值合并、没有加密密钥管理，适合小型教学平台与演示部署。
